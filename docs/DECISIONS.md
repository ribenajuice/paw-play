## 2026-09-25 — Best scores: one private SharedPreferences file, one clamped integer per game, kept out of backup
- **Context**: the founder approved a saved best score for Paw Blocks and Paw Pop (PRD stories 70-71). It is the first thing the app ever remembers, so it reverses the "No persistence in Milestone 1" entry below. Requirements: one whole number per game (0 to 999,999), nothing else stored, never leaves the phone, a broken or full disk never shows an error, and reading or writing never holds up a frame.
- **Decision**: (1) **SharedPreferences, not DataStore.** Framework API, so no new dependency, no new permission and no network code; `app/build.gradle.kts` stays as it is. One file, `paw_play_bests`, private mode, two integer keys: `best.paw-blocks` and `best.paw-pop`, each defined in its own game's package (never in a shared list, so the shell and the other game know nothing about them). Nothing else is ever written: no name, date, history, board, paws or stage. (2) **Failure rules.** A value that is absent, not an integer (a `ClassCastException` on read), negative or over 999,999 counts as 0; a score is clamped to 999,999 before it is compared or written; every read and write sits in a try/catch that swallows the failure. The best is always held in memory first (`BestScore.best`), so if a write is refused the good-game screen still shows the right number for the rest of the app session, because the in-memory object is process-wide and survives leaving and re-entering a game. (3) **Threads.** The read (`BestScore.load()`) runs inside `withContext(Dispatchers.IO)` when a game screen opens; `MainActivity.onCreate` also calls `getSharedPreferences` once, which only starts the platform's own background load of the file, so the read is normally already done when the child taps a tile. The game shows its home button at once and the play area as soon as the read returns (bounded by `withTimeoutOrNull(500)`, after which the best counts as 0). Writes use `apply()`, which updates memory at once and writes to disk on the platform's own background thread; `commit()` is never used. `load()` merges with `max`, so a score submitted before a slow read finishes is never lost. (4) **Save moment.** `BestScore.submit(score)` is called whenever the score goes up (a few times a minute at most), and writes only when the score beats the stored best; equal does not. So leaving by home, back or closing the app never loses it. The good-game screen "new best" flag is computed by the session as `score > bestBefore`, where `bestBefore` is the best captured when that game started, not by a latch in the storage helper. (5) **Where it lives, and how it stays testable.** New package `com.pawplay.app.data`: `BestScore.kt` is pure Kotlin (an `IntStore` interface with `read(key): Int?` and `write(key, value)`, and the `BestScore` class holding the clamping, `load`, `submit`, `best`, `MAX = 999_999`), unit-tested in `app/src/test` with a fake `IntStore` that throws, returns junk and fills up; `BestScores.kt` is the Android glue (a process-wide map of keepers by key, `SharedPrefsIntStore`, the `warmUp(context)` call and a `rememberBestScore(key)` composable). A game passes only its own key, so Blocks and Pop never import each other or each other's key. (6) **No reset.** No in-app reset, per the PRD; a parent clears the app's storage in Android settings.
- **Alternatives**: Jetpack DataStore (Preferences) — rejected: adds `androidx.datastore` for one integer, no safer on disk, and its coroutine API makes the "swallow every failure, keep the best in memory" rule longer to write. Room or a JSON file — rejected, far more machinery than one number. A shared "all scores" class in one place — rejected, it would make one game able to read or overwrite the other. `commit()` on an IO thread — rejected, `apply()` is enough and cannot block a frame.
- **Consequences**: the third-party dependency table is still empty and the app still needs no permission. `docs/ARCHITECTURE.md` "Preferences (Future)" is now real but narrow: only these two keys. If a game ever wants to save more, that is a new ADR and a new PRD decision, not an addition to this file. Process death loses the game in progress (only the best is saved), as the PRD intends.

## 2026-09-25 — The saved number never leaves the phone: no backup, no device transfer, no network
- **Context**: story 70 says the best is "not included in cloud backup or phone-to-phone transfer". Today `AndroidManifest.xml` has `android:allowBackup="true"` and no rules file, so Android would back the new preferences file up to the parent's Google account and copy it to a new phone. The manifest has no `<uses-permission>` at all, so the app has no `INTERNET` permission and cannot reach a network (checked 2026-09-25); the debug-only `ui-tooling` and `ui-test-manifest` libraries add no permission to a release build.
- **Decision**: in `app/src/main/AndroidManifest.xml` set `android:allowBackup="false"` and also point `android:fullBackupContent` at `res/xml/backup_rules.xml` (Android 11 and older) and `android:dataExtractionRules` at `res/xml/data_extraction_rules.xml` (Android 12 and newer, with both the `cloud-backup` and `device-transfer` sections). Both xml files exclude every domain (`root`, `file`, `database`, `sharedpref`, `external`) with `<exclude>`, so the intent survives if someone later flips `allowBackup` back on. A new pure-JVM test (`AppPrivacyTest`, in `app/src/test/java/com/pawplay/app/data/`, reading the manifest and both xml files the way `TraceGlyphsTest` reads the glyph doc) fails if `INTERNET` or any other permission appears, if `allowBackup` is not `false`, or if either rules file stops excluding the `sharedpref` domain. The security-reviewer's pre-release check should also read the merged release manifest, not only the source one.
- **Alternatives**: `allowBackup="false"` alone — probably enough, but three lines of explicit rules cost nothing and make device transfer explicit. Excluding only the one preferences file by name — rejected, an allow-nothing rule is simpler to trust and nothing else is stored.
- **Consequences**: a reinstall or new phone starts both bests at 0, which the PRD accepts. There is nothing else in app storage to lose.

## 2026-09-25 — Shared pieces for the two scored games: `data/` and two `ui/` files, and the independence rule stays
- **Context**: Blocks and Pop both need the same good-game screen, the same paw pictures and the same saved-best helper, and story 73 says they must not depend on each other. The home button, sparkle and animal drawings are already copied into six packages (see the Paw Trace and Paw Pop entries below); copying a whole ending screen and its timing rules a seventh and eighth time would be worse, because the "0.6s touch guard, exactly once" rule must be identical in both.
- **Decision**: (1) `ui/GoodGameScreen.kt`: one composable, `GoodGameScreen(score: Int, best: Int, isNewBest: Boolean, animal: @Composable (Modifier) -> Unit, onPlayAgain: () -> Unit, onHome: () -> Unit, modifier: Modifier = Modifier)`. The game supplies its own smiling animal through the `animal` slot (Blocks its corner critter, Pop one of its four animals), so `ui/` imports nothing from any game's drawings. It owns: the 0.5s fade-in, the softly dimmed backdrop, the score and best numbers with the rosette (drawn in `ui/`), the two 72dp+ buttons 24dp apart, the new-best glow, hop and sparkle (about 2s, at most 3 flashes a second), and the input rules: both buttons ignore touches for the first 0.6s, and a single latch (`GoodGameGate`, pure Kotlin in `ui/GoodGameGate.kt`, unit-tested: `accept(elapsedMs): Boolean` is true at most once and only from 600ms) means a double-tap on play again starts exactly one game and home plus play-again together do only the first. (2) `ui/PawLives.kt`: `PawLivesRow(paws: Int, fadingIndex: Int?, fadeStartMs: Long, nowMs: Long)` draws three pictures, a full paw or an outline that differs in greyscale, fading one over 0.6s; and `ScoreNumber(value: Int)` with the under-0.4s count-up (a plain animated integer, no flash, bounce or colour change). (3) `data/` as in the best-score entry above. (4) `ui/` and `data/` may import the two public Paw Match icons (`HomeGlyphIcon`, `PawPrintIcon`) that every game already imports, and nothing else from a game, until the queued follow-up moves the shared drawings into `ui/` for all games. (5) `PawBlocksIndependenceTest` and `PopIndependenceTest` keep failing on any import between Blocks, Pop and the other games; extend the scan so `ui/` and `data/` importing any `games/` class other than those two icons fails as well, and so a game importing another game's file still fails.
- **Alternatives**: a private copy of the ending screen inside each game (like the home button) — rejected, the guard and latch rules would drift. Putting the screen inside the Paw Blocks package and having Pop import it — rejected by story 73. Widening `MiniGame` with a "best score" hook — rejected, four of six games have none, and the 2026-09-22 ADR says the contract only widens deliberately.
- **Consequences**: the win overlays of Match, Pour, Kitchen and Trace are untouched. When the shared-drawings follow-up happens, the two public icons move into `ui/` and the allowance in (4) disappears.

## 2026-09-25 — Paw Blocks: score, 3 paws and a game over live in `BlocksSession` (supersedes "no score, no lose")
- **Context**: stories 63-65 and 72. The 2026-09-24 Paw Blocks entry said "no score, combos, timer or counters", and its follow-up said the clear-out could never end the game. Both are superseded for score, paws and ending; the rest of that entry stands (ramp, board sizes, blocks, drag, dealer, clear-out picking, tray).
- **Decision**: all rules stay in the pure, unit-tested `BlocksSession`; the screen only draws them. (1) **Scoring** in a new `PawBlocksScoring.kt` (pure): `PLACE_POINTS = 3`; `lineBonus(lines)` is 0, 10, 30, 60, 100 for 0, 1, 2, 3, 4-or-more lines, where `lines = rows.size + cols.size` of that placement (a double line scores as two lines but is still one clear for the ramp); `MAX_SCORE = 999_999`, the score is clamped. Clear-outs, refills, growth, wrong drops and cancelled drags add and take nothing. `Placed` gains `points: Int`. (2) **State** added to `BlocksSession`: `score: Int`, `paws: Int` (starts at `BlocksRamp.START_PAWS = 3`, only ever goes down), `phase: BlocksPhase` (`PLAYING` or `GAME_OVER`), `gameOverAt: Long`, and a constructor argument `bestBefore: Int = 0` with `isNewBest: Boolean get() = score > bestBefore` (equal is not new). `startScore` and `startPaws` constructor arguments exist for tests. (3) **The one rule** is inside the existing clear-out branch of `tick`: when `isStuck` (story 45's exact condition, none of the blocks left in the tray has a legal spot) and not holding, growth is not pending, and `nowMs >= max(lastMoveAt, busyUntil) + 1000ms`: if `paws > 0` then clear out as before, `paws--`, and emit `ClearedOut(rows, removed, pawsLeft)` (the screen fades that paw over 0.6s); else set `phase = GAME_OVER`, `gameOverAt = nowMs` and emit `GameEnded(score)` once. The clear-out board always has a fitting block afterwards, so the same stuck state cannot fire twice, which is what makes it one paw per clear-out however many rows it takes, and a fresh tray is never stuck (story 44). `busyUntil` keeps game over out of a line-clear animation, `holding` out of a held block, and `setHolding` records the let-go moment, so "one second after his last move" holds. (4) **After game over** `place` returns null, `setHolding` and `tick` do nothing, `hasPending` is false so the frame loop rests. (5) **Play again** is a new `BlocksSession` (the screen keeps a game counter and keys `remember` on it), with `bestBefore = BestScore.best` at that moment; leaving and coming back is the same. (6) **The screen**: `BlocksScene` calls `best.submit(session.score)` whenever the score changes, shows `ScoreNumber` opposite the home icon and `PawLivesRow` beside it in the top strip (never under a dragged block: the strip's y-range is above the board, and `DragTracker` already clamps the ride height), and when `phase == GAME_OVER` draws `GoodGameScreen` over the dimmed board with the corner animal. Layout numbers for the strip come from `docs/DESIGN-SYSTEM.md` and go into `PawBlocksLayout.kt` as plain numbers like the rest.
- **Alternatives**: keeping score in `BlocksUi` (rejected: it must be unit-tested and must survive the screen redrawing); ending the game the moment the last paw is spent (rejected by the PRD: a second of peace after his last move); a paw per row cleared out (rejected: one paw per clear-out).
- **Consequences**: existing tests that assert "the clear-out never ends the game" or "a full board always recovers" in `PawBlocksSessionTest`, `PawBlocksFollowUpTest` and `PawBlocksQaTest` must be rewritten to the paws rule, not deleted; add tests for every points row, a wrong drop, a cancelled drag, 3 clear-outs then game over, no game over while holding or during a line-clear animation, one paw per clear-out under a per-frame `tick`, `GameEnded` exactly once, and `isNewBest` equal versus greater. After game over the backgrounding rule is the existing one: deadlines are compared with the frame clock, so a deadline that passes while the app is away fires on the first frame back; that is accepted and needs no clamp.

## 2026-09-25 — Paw Pop: zig-zag legs, an entry line, 3 paws with a grace window, and a game over (supersedes "no lives, no game over" and the sine sway)
- **Context**: stories 51, 56, 60, 61, 66-69, 72. The old Pop entries said "no lives, damage, score, timer or game over", swayed every target on a sine, dropped the first target already partly on screen, and pinned the pace to straight-drop measurements. All of that is superseded where it conflicts; the single clamped time step, pools, hard limits, steering and hand-over, gifts, effects and drawing entries stand.
- **Decision**: every rule stays in the pure `PopSession`, advanced only by `step(dt)`; the screen draws it.
  1. **Paths.** New pure file `PopPath.kt`. A `PopTarget` loses `x0`, `amp`, `phase` and gains `speed` (downward, in screen heights a second), `side` (0 while on the entry leg, then -1 or +1), `legLeft` and `sinceTurn` (seconds), `entered` (latched) and `sinceEntered`, `missed` (latched). Each step: `vy = speed * height * slowFactor`, capped so the path speed `vy / cos(angle)` never exceeds 0.2 * height (`PopMetrics.MAX_PATH_SPEED`); `vx = side * vy * tan(angle)`; a plain straight line between turns, no easing. `legLeft` counts down from a run length drawn from the stage's range (starting when the target has entered, so the first turn is never in the first 0.5s after it does, `NO_TURN_AFTER_ENTRY`); at zero the target turns instantly: the first turn picks a random side, every later one alternates, a new run is drawn, and from stage 3 the speed is re-drawn within plus or minus 25% of the old one (`REPICK_LIMIT`) and inside the stage's range. Slow drift multiplies vy and therefore vx by 0.5 and does not change the run timer (the leg then covers half the distance).
  2. **Sides.** A target whose body (size / 2) would come within `EDGE_CLEAR` (8dp) of a side edge turns early if at least 0.9s (`MIN_TURN_GAP`) has passed since its last turn; if not, it is pinned to the limit for that step and slides down the wall until the gap has passed. So no target ever leaves the sides and no two turns are closer than 0.9s, both asserted in a test over many seeded sessions and every stage. On resize (`setArea`) x scales with the width and is clamped inside the margins; y scales with the height; the `entered` latch is not undone.
  3. **Entry.** New `PopMetrics.SKY_TOP` (dp from the top of the play area; the number comes from `docs/DESIGN-SYSTEM.md`, the same line where stars twinkle out and where the score and paws strip ends). A target spawns with its whole drawn body above the line (`y + kind.halfHeight * size <= SKY_TOP`, using the existing `TargetKind` numbers) and heads straight down. It becomes `entered` when `y - kind.top * size >= SKY_TOP`, and a single function `isPoppable` (entered, not missed, phase `PLAYING`) is checked by star hits, big-star hits, the ribbon and the wave; all four skip a target that is not poppable, so nothing can pop what is still coming in. Stars are removed when they reach `SKY_TOP` (replaces `STAR_EXIT_MARGIN`). The `FIRST_TARGET_TOP` special case is deleted: the first target also enters from above and is made 0.05s after the start, so it is visible within a second (the screen clips drawing at the line; if the designer wants it drawn across the strip that is a drawing choice, not a rule). The wave and "the screen is empty" shortcut count only targets that are on the list: the wave's "at least one ordinary target on screen" means an ordinary target that is poppable.
  4. **Sizes.** Per stage from the PRD table, never below 56dp (`MIN_TARGET_SIZE`) and critter bubbles never below 64dp (`MIN_CRITTER_SIZE`). Stage 5's "about 1 in 3 is 56-64" replaces the old 72dp `smallChance` rule (chance 1/3, then a size drawn from 56-64). **Carriers now use a floor of 72dp (was 96)**, because 96 would exceed stage 4 and 5's sizes and carriers are meant to be ordinary in every other way; the 48dp gift picture still fits inside 72dp. This is a default the developer applies; the founder can change it if a carrier looks too small.
  5. **Paws, score and phase.** `PopSession` gains `paws` (starts at `PopMetrics.START_PAWS = 3`), `score`, `phase` (`PLAYING`, `ENDING`, `OVER`), `graceLeft` (seconds, 0 when off), `bestBefore` (constructor argument, default 0) and `isNewBest = score > bestBefore`. Each pop adds 1, a carrier 3 (`POP_POINTS`, `CARRIER_POINTS`), by any route because everything goes through one `pop()`; gifts and effects add nothing; `MAX_SCORE` 999,999 clamp. A target that starts to fade (`alpha < 1`, latched into `missed` so it counts once and can no longer be popped) costs a paw only if it is not a carrier and `graceLeft <= 0`; that sets `graceLeft = 3s` (`GRACE_SECONDS`), decremented in `step` so a backgrounded app never uses it up, and the screen glows the ship while it is above 0. Several targets missing in the same step cost one paw in total. Nothing regains a paw and no gift touches `paws`.
  6. **Ending.** When `paws` reaches 0: `phase = ENDING` for `ENDING_SECONDS = 0.5`; firing, spawning, gifts, effects, stars, the ribbon, the wave, pops, points and steering all stop, remaining targets fade out over the 0.5s, then `phase = OVER` (one transition, once). The screen shows `GoodGameScreen` when it sees `OVER`. `touchDown/Move/Up` are ignored once `phase != PLAYING`. Play again is a new `PopSession` (same rule as Blocks); leaving and coming back is the same. The screen calls `best.submit(session.score)` whenever the score changes.
  7. **Ramp table and stage fields.** `PopStage` is replaced by the PRD's revised columns: `spawnEvery`, `maxTargets`, `minSize`, `maxSize`, `smallChance`, `driftMin`, `driftMax`, `turnDegrees`, `runMin`, `runMax`, `repickSpeed` (stage 3 and up), `kinds`, `colours`. The stage numbers come straight from the PRD table (3.5/3.0/2.5/2.0/1.7s; 4-8 on screen; sizes 88-96, 80-96, 72-88, 64-80, 56-72; drift 0.06-0.09, 0.06-0.10, 0.07-0.11, 0.07-0.12, 0.08-0.12; angles 20/30/40/45/50; runs 2.5-3.5, 2.0-3.0, 1.5-2.5, 1.2-2.0, 0.9-1.6). The old sine constants (`SWAY_SECONDS`, the sway column, `swayPhaseNow`) are deleted.
- **Alternatives**: a curved or eased zig-zag (rejected by the PRD: sharp turns are what lets a child learn to lead a shot); making targets un-poppable by position of the star instead of a flag (rejected: one `isPoppable` used by four routes cannot be forgotten by one of them); ending the game the instant the third paw fades (rejected: the 0.5s calm fade is in story 69); a fixed-step accumulator for grace (rejected, same reasoning as the 2026-09-25 clamp entry).
- **Consequences**: Pop's tests change a lot: `PopRampTest`, `PopQaTest`, `PopRobustnessTest` (the resize test used `x0` and `amp`), `PopShapesTest` and `PopTestSupport` need rewriting for the new fields, and every seeded replay changes because the random sequence changed. New tests: legs are straight (constant velocity between turns), turns alternate, the first side varies with the seed, no turn in the first 0.5s after entry, turn gap at least 0.9s and never outside the sides for many seeds at every stage, path speed never above 0.2 sh/s at any stage including slow drift, the speed re-pick within 25%, an un-entered target survives a star, a big star, the ribbon and the wave, a missed target survives them too, a carrier miss is free, one paw per grace window however many targets miss together, no paw cost for a pop or a gift, game over exactly once, points 1 and 3, nothing steers or scores after ENDING, a paused session (a huge `dt`) neither loses a paw nor ends the game.

## 2026-09-25 — Paw Pop ramp thresholds 24/60/108/165 are unverified; QA re-measures with scripted players
- **Context**: those numbers were measured (2026-09-25 QA entry below) against straight-drop, larger, non-scoring targets. Smaller zig-zagging targets are popped less often, so stages will arrive later, and a paw loss now ends the game, so pace matters more than it did.
- **Decision**: keep 24/60/108/165 in `PopRamp` for the first build and treat them as unverified. The QA engineer re-measures with the five scripted players from the earlier entry (a player who never touches the screen, a slow toddler tapping every 4 to 7 seconds, a sloppy wanderer, a busy tapper, perfect aim) over 40 seeds each, and reports against the PRD targets: a busy tapper loses at most 1 paw in the first 60 seconds (median); a never-touching player reaches the good-game screen between 30 seconds and 3 minutes; a perfect-aim player reaches stage 4 before running out of paws in most runs. If a target is missed, tune the ramp table numbers first (pop counts, spawn gaps, angles), not the rules. The old band tests in `PopRampTest` (perfect 130-220s, busy 160-260, toddler 270-450, never-touching over 300s) describe the retired game and must be replaced by these targets, not adjusted to pass.
- **Alternatives**: guessing new thresholds now (rejected: the last guess was 2.4 times off).
- **Consequences**: the scripted-player helpers in `PopTestSupport` need to model paws, so a player who never touches the screen actually ends. If a paw count of 3 is too harsh for him in real play, the count is one constant (`START_PAWS`).

## 2026-09-26 — Paw Blocks score built: a tap is not a drop, the best waits for its read, and the shared API as built
- **Context**: building phase 1 of the score work (Blocks plus the shared `data/` and `ui/` code) turned up three things the specs did not cover.
- **Decision**: (1) **A tap is not a drop.** The approved layout puts the board 36dp lower and the tray 12dp lower, so the gap between them is now 40dp (was 64). A block rides 64dp above the fingertip, so a finger that merely tapped a tray block and lifted put the block within snap reach of the board's bottom row and it landed. `DragTracker` now remembers how far the finger got from where it landed, and a lift under `Snap.TAP_SLOP_DP = 12dp` sends the block home like any other wrong drop. Every real placement moves the finger much further (the bottom row needs about 36dp of travel), so nothing legitimate is lost. Both the "a tap places nothing" and "wrong drop" tests are back to their old meaning and there are new tests for a tap, a 13dp drag and a wobble. (2) **`BestScore.submit` writes only after `load()` has looked at the store.** Before that a raised best is held in memory; `load()` then saves it if it beats what was stored, and a repeated `load()` retries a write that failed earlier. Otherwise a score submitted during a slow read (the 500ms cap lets a game start first) could overwrite a higher saved best. `submit` still never throws and `best` is always right in memory. (3) **The 500ms cap really caps.** The screen starts the read with `launch(Dispatchers.IO)` and waits on `join()` with `withTimeoutOrNull(500)`; a plain `withTimeoutOrNull { withContext(IO) { blocking read } }` would wait for the read to finish because a blocking call cannot be cancelled. A slow read carries on in the background and merges with `max` when done. (4) **Shared API as built** (for Paw Pop): `GoodGameScreen(score, best, isNewBest, animal, onPlayAgain, onHome, modifier, wash)`, where the extra `wash: Color` defaults to Blocks' cream at 84% and Pop passes its white 20%; the game draws its own animal (calm face, or the happy one when `isNewBest`) and its own corner home button above the screen. `PawLivesRow(paws, fadingIndex, fadeStartMs, nowMs)` reads "paws left now" and the index of the paw that fades (equal to `paws` right after a loss); `PAW_FADE_MS` is exported, the caller clamps `nowMs` to the fade window so the row is not recomposed each frame. `ScoreNumber(value)` is the top-strip number; digits are drawn at design sizes whatever the phone's font-size setting is. `GoodGameMotion` (pure) holds the hop, glow and twinkle timings and is unit-tested against the three-flashes-a-second rule. (5) **Layout give-way order kept** as the design says (tray margin 60 to 12, slot height 112 to 72, gap 40 to 12, top 132 to 96, then the panel), which costs a little on the shortest windows: a 9x9 cell is 35.6dp at 360 x 520 (was 36.9) and the stage-6 tray cell is 13dp at 320 x 568 (was 16). Both are far below real phones and the tests say so.
- **Alternatives**: making the tray gap bigger again (rejected: the founder saw and approved the mockup's numbers); refusing any drop whose finger is inside the tray (rejected: a bottom-row placement legitimately needs the finger in the top of the tray); writing to the store at once and merging later (rejected: it can lose a higher saved best).
- **Consequences**: the touch rule for Blocks changed by one line of behaviour; Paw Pop is unaffected. `docs/DESIGN-SYSTEM.md` "Drag, ghost and snap" gets the tap rule.

## 2026-09-25 — The app is no longer restarted by configuration changes
- **Context**: story 72 says score, paws and a showing good-game screen must be kept across rotation and backgrounding. The activity is locked to portrait, but Android still recreates it for a dark-mode switch, a font-size or display-size change, or a language change, and `PawPlayApp` holds "which game is open" in `remember`, so today any of these silently throws the child back to the home shelf and discards the game in progress, the score and the good-game screen.
- **Decision**: add `android:configChanges="orientation|screenSize|smallestScreenSize|screenLayout|uiMode|density|fontScale|locale|layoutDirection|keyboard|keyboardHidden"` to `MainActivity` in the manifest, so the activity survives these and Compose simply recomposes. No ViewModel, no saved-state plumbing, no new dependency. Process death still loses the game in progress (only the best survives), as the PRD intends.
- **Alternatives**: `rememberSaveable` or a ViewModel for every game's session (rejected: sessions hold random generators, pools and pure-Kotlin state that would need serialising, for a case that is one manifest line).
- **Consequences**: applies to all six games and is only an improvement for the four that have no score. A device test is still needed: change font size or dark mode mid-game and confirm the game carries on.

## 2026-09-24 — Home screen menu built for ~a dozen games from the start
- **Context**: founder confirmed the long-term plan is roughly a dozen small games on the shelf, and asked for "a menu where we can select the game from" as the next step, ahead of brainstorming which games. The home screen already existed but only rendered one tile (`games.size == 1` special case) and hadn't been exercised with a real multi-tile grid.
- **Decision**: extracted the adaptive-column layout from the 2026-09-23 entry below into a shared `AdaptiveSquareGrid` composable and used it for both the home screen's tile grid and Paw Match's card grid, instead of duplicating the logic or leaving the home screen's multi-game case untested. ## 2026-09-24 — Paw Pour: search-based solver, budgeted; small rule choices
- **Context**: Paw Pour must never deal an unwinnable round (story 14) and must notice mid-round when the child has made the round unwinnable, including when pours remain (story 17, broad "stuck"). Boards are small (at most 9 tubes of 4) but proving a dead position dead means exhausting everything reachable from it.
- **Decision**: one depth-first search (`PawPourSolver.kt`) answers both questions. Positions are packed into ints and treated as equal when they differ only by tube order; only one empty tube is tried as a target. It has a node budget (300,000); if it runs out the answer is `UNKNOWN`, which generation treats as "reject this deal and re-deal" and mid-round play treats as "still finishable" (so a slow check can never cost the child progress). Measured on a desktop JVM: a check takes about a millisecond typically, ~3ms worst over 118,000 positions from random play, and the budget was never hit; it still runs on `Dispatchers.Default` so a slow phone can't stall the screen. Auto-undo needs no re-solving: after every pour the position is checked and `safeDepth` remembers the latest finishable one, so "latest position that can still be finished" is just `safeDepth`. Input is locked until each check returns, which keeps that record complete.
- **Also decided**: (1) Win rule, superseded by the founder on 2026-09-25: a round is won only when every colour is gathered into one tube, i.e. every non-empty tube is full and a single colour (`Board.isSolved`). The first build used the PRD's looser "every tube empty or one colour", which let a colour split across two part-full tubes count as won. A split position is never stuck (a merging pour always exists), and the win now always agrees with the finished-tube border and sparkle. (2) A second tap that isn't a legal pour always gives the gentle wobble and puts the selected tube down (story 12); it does not switch selection to the other tube (story 10 also reads that way for a different-colour tube; the two stories conflict there, and the wobble is the kinder feedback). One place to change: `Board.tap`. (3) Finished and empty tubes cannot be picked up. (4) Paw Pour repeats Paw Match's small private exit button / win overlay instead of importing them, so neither game depends on the other's internals; the shared icons are the public ones in `AnimalIcons.kt`. Worth moving all of it to `ui/` when the third game arrives.
- **Alternatives**: a dead-end lookup table or hand-written "no move left" rule only — rejected, story 17 needs the broad reading. Random deals without a solver plus a repair step — rejected, the solver is cheap and makes the guarantee simple. A solver library — rejected, no new dependencies.
- **Consequences**: the rules are in one file (`PawPourLogic.kt`) and are unit-tested, including 150 generated boards for each ramp round 1-8. If a future round size makes the budget bite, the fallback reading (unknown = keep playing) is already safe; raise the budget or add symmetry pruning then.

## 2026-09-25 — Paw Trace: our own tiny path parser, sampled strokes, and the finger rules
- **Context**: Paw Trace has to decide, on every touch event and on a slow phone, whether a finger is on a stroke, how much of each stroke is painted, and where the frog stands. That logic must be unit-testable without a phone, and the glyph data is 46 SVG-style strings the designer drew.
- **Decision**: (1) **Parser and sampler.** `TraceGeometry.kt` parses only the subset the data uses (absolute `M`, `L`, `C`; anything else throws, and a test rejects a dozen bad strings) and samples each stroke evenly by arc length every 1.5 glyph units (curves are first flattened into 64 straight bits each; sample count is `round(length / 1.5)`, first and last samples are pinned exactly on the path's ends). Compose's own `PathParser` and `PathMeasure` were not used for the logic because they need Android or Compose on the test classpath; Compose's `PathParser` is used only to draw the sparkle and heart. The guide itself is drawn from the exact curves, the paint from the samples. (2) **Coverage.** A touch counts if it is within 32dp of a stroke's centreline, measured to the nearest point on the sampled polyline (not just the nearest sample), inclusive at the edge. The 32dp is turned into glyph units for the box the screen actually got (a 288dp box is 11.1 units, a 320dp box 10), so the corridor is always a fingertip's width whatever the picture size. It paints the nearest sample plus 2 either side (3 glyph units; the design doc says both "3dp" and "3 units", the mockup uses 3 units) on every unfinished stroke in range, so a finger at a join paints both strokes. A stroke is done at 85% of its samples covered (inclusive), then its remaining samples are marked covered and the screen fills the gap over 250ms; the model keeps what a finger really painted (`touched`) separate from `covered`. A swipe between two touch events is stamped every 2 units so a fast finger leaves no holes. (3) **Marker.** As in the mockup: on the stroke being painted (else the first unfinished one), 48dp past the first gap, exactly on the start while the start is unpainted. (4) **Fingers.** Only the first finger paints, from wherever it lands on the screen (a finger on the home or play-on button belongs to that button). One small addition: if the first finger has never yet been on a path (a resting palm, say) a later finger that lands on a path takes over, so a palm can never make the game seem broken; once the painting finger has been on a path it keeps the job until it lifts, and then the next new touch takes it. If the screen ever sees no finger down, it forgets every finger (a missed lift can not strand the game). A finger still resting on the glass when a new glyph appears does not paint it until it lifts and lands again. (5) **Ramp.** "Every third glyph" is counted from the first shape: new, new, earlier-stage, repeating, and the count carries across stages (so the first glyph of each new stage is new, unless it lands on the third slot). A mixed-in glyph never counts towards advancing; the glyph just played is never repeated. (6) **Layout.** The glyph box is 320dp at most and 288dp at least: side margins are 20dp and shrink to 16dp on a 320dp-wide phone before the box shrinks. It is centred vertically unless that would sit within 16dp of the home button or the play-on button; the play-on button's bottom margin (44dp) shrinks to 12dp before the glyph moves or shrinks below 288dp. On a screen under about 496dp of usable height the play-on button can overlap the foot of the glyph, but it only exists on the celebration. (7) **Sound.** Paw Trace ships silent like every other game; the chime and happy sound in stories 33 and 35 are unmet until the founder decides on sound app-wide.
- **Also decided**: the glyphs are Kotlin data (`TraceGlyphs.kt`), and `TraceGlyphsTest` reads `docs/glyphs/paw-trace-glyphs.md` and fails if the two ever differ. The designer's file says every glyph except its list of 19 has one stroke, but X is two crossing diagonals in both the file's data and the mockup; the list was the slip and is corrected. R's leg starts on the bowl and is 16 units from the stem (the design rule is 20 for strokes that do not join); it is joined through the bowl, so the bands only overlap where the glyph joins, and a test states that exception. The frog's face is drawn inside the Paw Trace package (`TraceFrog.kt`): the same colours, grid recipe, smile and happy grin as Paw Kitchen's customer frog, cropped tight, so Trace does not import Kitchen. The home button, the sparkle and the heart are also copied into the Paw Trace package (they are private in the other games), so there are now four copies of the home button and three of the sparkle drawing; they, and the win overlays, should move to `ui/` in one follow-up that touches all four games together. Until then a unit test holds independence: nothing from Paw Kitchen or Paw Pour, and from Paw Match only the public icons Pour and Kitchen also use (`HomeGlyphIcon`, `PawPrintIcon`). (6b) **Touch layer (2026-09-25, after QA).** Touches are read by one full-screen layer under the buttons, not by the glyph box, because a swipe that started in the blank space and slid onto the path painted nothing until the finger lifted and landed again. The first-finger and palm rules are unchanged. **Drawing (after review).** The guide, the stroke polylines and the shimmer paths are built once per glyph and size and reused; only the paint paths are rebuilt, and only when the painting actually changed; finished strokes are drawn once, not twice.
- **Alternatives**: `PathMeasure` for sampling (needs Android in the tests). Nearest-sample-only distance for the corridor (up to 0.75 units of error at the edge, and it makes the edge tests approximate). One paint mask per pixel (heavier, and stroke-based completion is what the design measures). Letting any later finger paint (a resting palm or a second hand smears paint across the glyph).
- **Consequences**: adding a glyph is one line in `TraceGlyphs.kt`; the tests then check it parses, stays in the safe box and can be finished. If sound or a lowercase set arrives, the stage list and `RampState` are the only places that change. The glyph box floor of 288dp needs 320dp of screen width and about 500dp of usable height; smaller than that, the game still plays but the glyph shrinks below the design floor (flagged to the designer).

## 2026-09-25 — Paw Blocks: how the tray is dealt, how the clear-out picks rows, and where the timing lives
- **Context**: three rules pull against each other. The tray must always have a block that fits (hard), should be placeable as a whole (best effort), should offer a line-finishing block on big boards (best effort), must be random, and must never repeat the last trio. The clear-out must be predictable, quiet and never loop. And every wait (0.5s refill, 1s clear-out, growth after the animation) must be testable without a phone.
- **Status (2026-09-25)**: the clear-out (2) now happens at most 3 times a game, one paw each, and with no paws left the game ends instead (see "Paw Blocks: score, 3 paws and a game over"); the "never loop" and "ends when the board is empty at the latest" properties still hold for each clear-out. The dealer, timing model, ramp and layout stand.
- **Decision**: (1) **Dealer.** `TrayDealer.deal` draws up to 48 random trios from the stage's set and ranks each: not the same trio as last time (4 points), all three placeable one after another with lines cleared between (2), a line-finishing block included on boards 7x7 and up (1); a trio with no placeable block is never used (hard). Every second attempt forces a line finisher in. It stops early on a perfect trio and otherwise takes the best seen; on a board so tight that no random trio has a placeable block it puts one placeable shape in on purpose (the dot fits any empty cell, and a board is never full because full lines clear). "Placeable in some order" is a depth-first search over the six orders and every legal spot, capped at 20,000 placements, and a capped search answers yes (that many ways to place things means there is room). This gives random blocks, keeps the hard guarantee cheap, and lets the best-effort rules degrade one at a time. It is tested against an independent brute-force check in the unit tests. (2) **Clear-out.** `GentleClearOut.clear` orders rows by how many cells they hold (fullest first, top row on ties), removes a third of the height rounded up at a time (2 on 5x5 and 6x6, 3 on 7x7 to 9x9) and repeats only until one remaining tray block fits; whole rows only, so nothing moves and the result is predictable; it ends at the latest when the board is empty, which fits everything. It never touches `clears`. (3) **Timing.** `BlocksSession` takes the time as an argument (`place(..., now)`, `tick(now)`); the screen feeds it its frame clock and the tests feed it a virtual one. Growth, refill and clear-out are deadlines, not timers: growth waits for the line-clear animation and for any held block, refill is 500ms after the last of the three and every animation, clear-out is 1s after his last move (a let-go counts) and never under a held block. A frame loop runs only while something needs it. (4) **Ramp.** Stage thresholds are cumulative clears 3, 8, 15, 24, 35; a placement that completes several lines adds one. (5) **Copies.** The animal (the six Paw Match critters with Paw Kitchen's happy face), the home button, the sparkle and the drawing helpers are copied into `games/pawblocks/` so it depends on no other game; only the two public Paw Match icons are imported, held by `PawBlocksIndependenceTest`. These copies should move to shared `ui/` in one follow-up that touches all five games (there are now five copies of the home button). (6) **Silent.** The design mentions a plop, a rising chime and a whoosh; like every other game, Paw Blocks ships silent until the founder decides on sound app-wide. (7) **Screens.** On phones wider than 360dp the panel and tray keep the design's sizes and centre; on narrower ones the panel shrinks to the width minus 32dp, and on short screens the tray's bottom margin, slot height, gaps and top margin give way in that order before the panel does. The board's cell size follows the panel (320 / N on the reference screen).
- **Alternatives**: choosing the tray by building it from cells that fit (exact but predictable and it would offer the same few blocks); a fixed-size random attempt count with no fallback (could deal an unplayable tray); real timers or coroutine delays for the waits (needs waiting in tests, and a delayed refill can fire twice); clearing whole columns or a random set of rows for the clear-out (harder to predict); a bigger board on wide phones (a design decision, left for the founder).
- **Consequences**: if a future stage adds a block, the dealer, clear-out and session need no change; a new block is one entry in `BlockShapes` and the ramp table. The best-effort rules can be tuned by the rank weights or the attempt count without touching the guarantee.

## 2026-09-25 — Paw Blocks after QA and review: cancel is not a lift, a bigger board, a bounded dealer
- **Context**: QA found that a system-cancelled touch (a back-gesture swipe, a notification pull-down, an app switch) placed the block at the ghost's spot, that 9x9 cells were 31dp on a 320dp phone (the PRD says about 36dp), and that the outer tray slots sat on the back-gesture strip. Review found that every pointer move woke the frame loop, that one deal could search up to 48 x 20,000 placements in the frame callback, that a block dropped into a line that was still fading was drawn under the old cells, and several per-frame allocations.
- **Decision**: (1) Compose reports a cancel as an "up" that is already consumed when it reaches the touch layer (checked against the desktop renderer by cancelling the pointer processor, in the QA probe and the render harness). `BlocksUi.onPointer` sends a consumed up to `cancelDrag`, so the block glides home; only an unconsumed up may drop. (2) The board panel is 6dp from each side and at most 348dp wide (was 328 with 16dp margins): 9x9 cells are 37.8dp at 360 wide and 33.3dp at 320 wide, which is about what nine cells can have on 320dp; the panel does not change size when the board grows, so nothing jumps. The tray is 96 x 112dp slots 12dp apart, 24dp in from the sides (82.7dp wide on a 320dp phone, never under 72), with tray cells 44, 29, 29, 22, 22, 17. On short windows the tray margin, slot height, gap and top margin shrink before the board does; 360 x 520 still gives 36dp cells at 9x9. A bigger board on wide phones stays a founder question. (3) The dealer keeps the first trio that has a placeable block before searching, then improves on it with a shared allowance of 12,000 searched placements per deal (5,000 per search); when it runs out the best trio so far is dealt and nothing unchecked is claimed. Measured on a desktop JVM over 8,500 boards including 9x9: mean 0.07ms, 99th percentile 0.3ms, worst 3ms, at most 2,429 placements searched, about 1.7 microseconds each; the allowance bounds a deal at roughly 20ms desktop, so it stays in the frame callback. (4) A faded cell of a cleared line is drawn only while its place is empty. (5) Only a drag starting or ending wakes the frame loop; the animal's paths, the per-stage block sets and the tray cell inputs are built once; the tray is read with `slot(i)`; there is one `svg` helper.
- **Alternatives**: treating any up outside the board as a cancel (would misread real lifts); dealing on a background thread (the allowance makes it unnecessary and adds a race with the refill deadline); tracking fading cells by epoch (a plain check of the current board is enough because a cleared place is empty until something is placed there).
- **Consequences**: story 40's "about 36dp" holds at 360 wide and up and is 33.3dp at 320 wide (documented, physical). The design numbers for the panel, tray and tray cells were updated in `docs/DESIGN-SYSTEM.md`.


## 2026-09-25 — Paw Pop: endless balloon-popping shooter with no lose state
- **Context**: founder wants a toddler-friendly Space Invaders. The genre normally has lives, speed pressure and enemies, none of which fit the standing rules.
- **Status (2026-09-25): partly superseded** by "Paw Pop: zig-zag legs, an entry line, 3 paws" above: plain targets that get past now cost one of 3 paws, there is a score and a saved best, and the game ends when the paws run out. "No lives, damage, score, timer or game over", "endless play" and "the only exit is the home button" no longer hold; nothing is hurt, and there is still no timer.
- **Decision**: **Paw Pop** (id `paw-pop`; renaming is content-only). Balloons and bubbles drift down; a friendly ship auto-fires stars every 0.4s and follows the newest finger's horizontal position anywhere on screen. ~~Misses float away harmlessly: no lives, damage, score, timer or game over.~~ Endless play with a gentle, capped ramp driven by a hidden pop count (5 stages, cap at 8 targets on screen). About 1 in 8 targets is a gift carrier; popping it releases a power-up (triple star, big star, rainbow ribbon, slow drift, sparkle wave) that glides to the ship by itself, so nothing can be missed. Effects fade with no countdown. Founder approved the spec, with both defaults (auto-glide gifts; stage-5 pace), on 2026-09-25.
- **Alternatives**: classic invaders with lives — rejected (lose state, violence). Waves with a celebration — rejected by the founder in favour of endless play. Catching power-ups by sliding under them — rejected as a silent "you lost" when missed.
- **Consequences**: no finishing point, so the only exit is the home button. Silent like the other games. If the busiest stage is too much in real play, lowering the cap is a one-line ramp change.

## 2026-09-25 — Paw Pop: one clamped time step, a self-contained scheduler, and hard limits
- **Context**: Paw Pop is the first game that runs on its own clock (a ship that fires every 0.4s, targets that drift, effects with timers) rather than only reacting to touches. It has to stay calm and identical on a 60Hz and a 120Hz phone, survive the app being backgrounded, and never let a burst of objects pile up on a small child's screen, with no way to test on a device from here.
- **Status (2026-09-25)**: still current except where the zig-zag entry above supersedes it: the sine sway, the first target starting partly on screen, "nothing here can end the game", and the size and limits of the target ramp. The single clamped step, scheduler shape, pools, hard limits and steering stand.
- **Decision**: (1) All rules live in a pure `PopSession` advanced by `step(dtSeconds)`, with one injected `Random`, so the whole game is unit-tested on a plain JVM and a seeded session replays exactly. (2) One step never covers more than 50ms (`PopMetrics.MAX_STEP`); zero, negative, infinite and not-a-number steps do nothing. A minute in the background therefore becomes a single 50ms step on return: no target teleports, no burst of spawns or shots, nothing to special-case with lifecycle callbacks. A variable step with a clamp, not a fixed-step accumulator, because everything moves linearly (a fixed step would only add catch-up loops that a long gap could turn into a burst). (3) The scheduler is a single timer: a target is made when the timer has run out and fewer than the stage's cap (never above 8) are on screen; the timer is then set to the stage's interval, or to 0.3s if no spot 12dp clear of the others was found in 10 tries, and is cut to 0.5s whenever the screen is empty (so the PRD's "within 1 second" holds with room to spare). Carriers use a counter: the first is the 5th target, then 6 to 9 ordinary ones between, deferred (never doubled) while one is still on screen; the gift is chosen when the carrier is made, never the same twice in a row. (4) Hard limits are enforced where things are made, not by clean-up: 8 targets, 15 stars (a shot that would go over is simply not made, the 0.4s beat carries on), 16 pictures, 60 sparkles (a pop over the limit plays without its sparkles; the total is a running count that a test recounts from scratch), 1 gift in flight. Stars and pictures live in fixed pools, so the frame loop makes no lists. (5) Steering: the newest finger to land steers and older fingers are ignored until they land again; a lift lets the ship finish gliding to where the finger was (so a tap moves it), a cancel or a finger that vanished leaves it where it is (a stale position must not pull the ship after a system gesture). Compose reports a cancel as an "up" that is already consumed, as in Paw Blocks. (6) The rainbow ribbon replaces the stars while it runs and pops what its column touches at once as it grows; every pop, by whatever means, counts toward the hidden ramp, so a strong power-up can make a session climb faster, which is accepted. (7) Sound is left out, like every game: pop and gift sounds are unmet pending the founder's app-wide decision.
- **Alternatives**: a fixed 1/60s step with an accumulator (rejected: catch-up loops); pausing by observing the lifecycle (rejected: the clamp is enough and cannot get out of step with the OS); making stars and sparkles on demand with no pools (rejected: harder to prove bounded); letting the wave count only targets past a line (rejected: the design says 3 or more on screen when the gift arrives).
- **Consequences**: the session exposes small `internal` switches for tests only (`holdFireForTest`, `holdSpawnForTest`, `arriveForTest`, `addTargetForTest`) so a schedule can be measured without the ship popping things; nothing in the game can read them. Because the empty-screen rule brings the next target within 0.5s, a strong power-up (the ribbon) keeps refilling and popping the sky, and carriers come a little more often than "about one in eight" would suggest by clock time (it is still one in 6 to 9 targets). The home button, sparkle and animal drawings are now copied into six packages; moving them to shared `ui/` is a follow-up that touches all six games.

## 2026-09-25 — Paw Pop after QA and review: finger hand-over, ramp pace, sparkle wave, resize
- **Status (2026-09-25)**: (1) hand-over stands. (2) resize of a sway centre and amplitude is **superseded** (no sway now; see the zig-zag entry). (3) the pop thresholds **24/60/108/165 and all the measured seconds are for the retired straight-drop game and are unverified**; see "Paw Pop ramp thresholds are unverified"; the band tests described in Consequences are to be replaced. (4) the wave rule stands, with "ordinary target on screen" now meaning a poppable one (fully below the entry line). (5) drawing stands.
- **Context**: QA and review found that (1) when the steering finger lifted while an older finger was still dragging, the older finger was ignored until every finger lifted; (2) `setArea` scaled a target's position but not its sway centre, so targets snapped back to the old width's column; (3) the pop thresholds of 10/25/45/70 made a perfect-aim child reach stage 5 in about 70 s and a child who never touched the screen in about 190 s, far under the PRD's 3-6 minutes; (4) the sparkle wave popped nothing in about 9 of 10 arrivals because it needed 3 or more targets on screen and counted carriers (which it skips) among them; (5) the still sky was probably re-recorded every frame, and a few per-frame allocations and precision limits remained.
- **Decision**: (1) **Hand-over rule.** The newest finger to land still steers. When it lifts (or is cancelled), the ship finishes the glide (lift) or stays (cancel), and nothing steers; an older finger that is still down takes over only when it has moved 8dp (`ADOPT_SLOP`) from where it was at that moment. So a finger that keeps dragging carries on within a blink, while a palm that landed first and rests (or jitters by a few dp) never captures the ship, and a palm does not pull the ship to its own resting position when a real finger lifts, because adoption steers by the finger's *new* position only after real movement. A palm that deliberately slides more than 8dp is treated as a finger: this is the accepted cost. Fingers are remembered in fixed arrays (10 at most, oldest forgotten); a finger whose landing was never seen (it landed on the home button) can never steer by moving; cancel-all forgets everyone. This changes the PRD's story 61 wording from "older fingers still down are ignored until they lift and land again" to "an older finger only takes over by moving". (2) **Resize.** A target's sway centre and amplitude are mutable and follow the play area: the centre scales with the width, and the amplitude shrinks if the whole sway would no longer fit, so every target stays inside after the area gets narrower. (3) **Pace.** Thresholds are 24/60/108/165 pops (was 10/25/45/70, about 2.4x), chosen by measuring five scripted players over 40 seeds (a player never touching the screen; a slow toddler tapping every 4-7 s; a sloppy wanderer; a busy tapper; perfect aim): median seconds to stage 5 are 401, 365, 238, 197 and 163 (was 189, 165, 109, 86, 69). Nothing else in the stage table changed. A child who never touches the screen still gets busy in about 6.7 minutes, because the ship shoots straight up the middle and pops what drifts through; the PRD's claim that a child who is just watching never gets busier was wrong and was rewritten. (4) **Wave.** It pops whenever at least one ordinary (non-carrier) target is on screen as the gift arrives, staggered as before; carriers neither count nor are popped; if none is there it only glitters. In a simulation of 3,118 arrivals at random moments across the five players and all stages, an ordinary target was on screen at 66.1% of arrivals (the old rule, 3 or more of any kind, at 10.4%). (5) **Drawing.** The sky is its own graphics layer with the gradient made once; strokes, layer bounds (a small ring of reusable rectangles snapped to 8dp), and the frame callback are made once; the ribbon uses a longer step on a tall area so its buffer reaches the top; drawing phases are wrapped in double.
- **Alternatives**: making an older finger take over at once when the steering one lifts (rejected: a resting palm would pull the ship to itself); never handing over (the old behaviour, rejected: a toddler's second finger dragging on is ignored); a longer slop or a time window (rejected: 8dp is enough to tell a tremor from a drag and needs no timer); scaling the pop thresholds by 2x exactly (measured at 2.0x: a perfect-aim child took 138 s and a slow toddler 306 s, so 2.4x was chosen); lowering the spawn rate instead of raising thresholds (rejected: it would change the calm the stage table sets).
- **Consequences**: the tests pin the pace in bands (perfect 130-220 s, busy 160-260, toddler 270-450, never-touching over 300 s and slower than every playing child). If real play shows the game is still too fast or too slow, the four thresholds are the only numbers to change. The wave is far more useful and pops more often, which also lifts the pop count (and so the ramp) a little more when it lands.
